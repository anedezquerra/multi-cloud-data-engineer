\subsection*{Week 6: Continuous Ingestion (Snowpipe \& Snowpipe Streaming)}
\par\noindent\textbf{Outcomes:} configure auto-ingest Snowpipe with SQS events, call the Snowpipe REST API, stream rows with the Snowpipe Streaming API, enforce exactly-once ingestion with channel offset tokens, keep micro-batch backlogs bounded, monitor and alert on pipe health.
\begin{itemize}[label=-]
    \dayitem{Monday}{Snowpipe Architecture: Event-driven auto-ingestion via SQS / Event Grid notifications.}
    \dayitem{Tuesday}{Snowpipe REST API for programmatic ingestion calls.}
    \dayitem{Wednesday}{Snowpipe Streaming API: Direct row-set streaming into Snowflake tables (sub-second latency). Exactly-once ingestion via per-channel offset tokens: the client attaches a monotonically increasing offset token to each row batch, Snowflake persists it with the committed data, and a retried batch re-sending the same token is discarded as a duplicate. Contrast with unbounded micro-batch backlogs: when producers outpace a pipe's load throughput, queued files/messages grow without bound, end-to-end latency climbs from seconds to hours, and catch-up credit burn spikes --- size ingestion for peak rate and alert on backlog depth, not just pipe errors.}
    \dayitem{Thursday}{\project{Configure an S3 bucket event notification to trigger a Snowpipe automatically whenever a new CSV arrives. Verify continuous ingestion using \texttt{SYSTEM\$PIPE\_STATUS}.}}
\begin{lstlisting}[language=SQL, caption={Snowpipe auto-ingest with SQS notification}]
CREATE PIPE raw_csv_pipe AUTO_INGEST = TRUE AS
  COPY INTO raw.events (id, payload, load_ts)
  FROM (
    SELECT $1, $2, CURRENT_TIMESTAMP()
    FROM @raw_stage/events/
  )
  FILE_FORMAT = (TYPE = CSV SKIP_HEADER = 1
                 FIELD_OPTIONALLY_ENCLOSED_BY = '"');

-- Show the SQS notification channel for the S3 event rule
SHOW PIPES LIKE 'raw_csv_pipe';
-- Wire notification_channel ARN into the S3 bucket
-- event configuration, then verify:
SELECT SYSTEM$PIPE_STATUS('raw_csv_pipe');
\end{lstlisting}
    \dayitem{Friday}{\usecase{Architect a real-time fraud detection ingestion pipeline processing credit card swipes using Snowpipe Streaming vs. traditional micro-batching.}}
\end{itemize}
\prodnote{Enable pipe error notifications via \texttt{ERROR\_INTEGRATION} (SNS/EventBridge) so failed loads page the on-call engineer; use the pipe's file-level load history (\texttt{INFORMATION\_SCHEMA.COPY\_HISTORY}) to retry only failed files, since Snowpipe is at-least-once and \texttt{COPY INTO} is idempotent per file for 64 days.}

\subsection*{Week 7: Change Data Capture (CDC) with Streams}
\par\noindent\textbf{Outcomes:} create standard and append-only streams, interpret \texttt{METADATA\$ACTION}/\texttt{METADATA\$ISUPDATE}, consume stream offsets transactionally with idempotent \texttt{MERGE} and dedup keys, join stream deltas to dimensions in near-real-time, detect and recover stale streams.
\begin{itemize}[label=-]
    \dayitem{Monday}{Snowflake Streams: Standard, Append-Only, and Insert-Only stream types. State management: a stream's offset is its consumption state --- it records exactly which change records have been committed downstream. Compare with Dynamic Tables, which maintain incremental-refresh state internally (changed micro-partitions plus dependency versions) and degrade to a full refresh when the defining query uses constructs incremental refresh cannot track or after base-table DDL --- a full refresh reprocesses the entire base, so keep frequently-changing layers incrementally refreshable.}
    \dayitem{Tuesday}{Understanding Stream metadata columns (\texttt{METADATA\$ACTION}, \texttt{METADATA\$ISUPDATE}, \texttt{METADATA\$ROW\_ID}).}
    \dayitem{Wednesday}{Consuming streams in idempotent \texttt{MERGE} statements for incremental updates: dedup keys (e.g. a change-event ID) make re-runs no-ops, and stream-to-dimension joins in the \texttt{MERGE} source subquery (or inside a Dynamic Table) enrich deltas in near-real-time. Watch SCD staleness: if the dimension layer refreshes more slowly than the fact stream, new facts may join to a missing or outdated dimension row; absorb late-arriving dimension members by loosening the dimension layer's target lag and re-running the idempotent \texttt{MERGE} instead of dropping unmatched rows.}
    \dayitem{Thursday}{\project{Create a primary target table and a Standard Stream over a landing table. Perform \texttt{INSERT}, \texttt{UPDATE}, and \texttt{DELETE} operations on the landing table, then write a \texttt{MERGE} statement to sync changes to the target.}}
\begin{lstlisting}[language=SQL, caption={Stream + MERGE CDC pattern}]
CREATE OR REPLACE STREAM raw.customer_stream
  ON TABLE raw.customer_landing
  APPEND_ONLY = FALSE;

MERGE INTO gold.customers AS tgt
USING raw.customer_stream AS src
  ON tgt.customer_id = src.customer_id
WHEN MATCHED AND src.METADATA$ACTION = 'DELETE'
  THEN DELETE
WHEN MATCHED AND src.METADATA$ACTION = 'INSERT'
  THEN UPDATE SET name = src.name,
                  email = src.email,
                  updated_ts = CURRENT_TIMESTAMP()
WHEN NOT MATCHED AND src.METADATA$ACTION = 'INSERT'
  THEN INSERT (customer_id, name, email, updated_ts)
       VALUES (src.customer_id, src.name, src.email,
               CURRENT_TIMESTAMP());
\end{lstlisting}
\begin{lstlisting}[language=SQL, caption={Idempotent stream MERGE with a dedup key}]
-- gold.order_events carries the dedup key event_id
MERGE INTO gold.order_events AS tgt
USING (
  SELECT event_id, order_id, status, event_ts
  FROM raw.order_stream
  WHERE METADATA$ACTION = 'INSERT'
  QUALIFY ROW_NUMBER() OVER (
    PARTITION BY event_id ORDER BY event_ts DESC) = 1
) AS src
ON tgt.event_id = src.event_id      -- dedup key match
WHEN NOT MATCHED THEN
  INSERT (event_id, order_id, status, event_ts)
  VALUES (src.event_id, src.order_id, src.status, src.event_ts);
-- The stream offset advances only if this transaction
-- commits; a failed run leaves the offset untouched, and

from snowflake.snowpark import Session
from snowflake.snowpark.functions import col, avg, current_timestamp

session = Session.builder.configs({
    "account": "xy12345.us-east-1",
    "user": "de_pipeline",
    "password": "<from-env>",
    "role": "ENGINEER",
    "warehouse": "ETL_WH",
    "database": "ANALYTICS",
    "schema": "SILVER",
}).create()

orders = session.table("bronze.orders")
customers = session.table("gold.dim_customers")

result = (orders
    .filter(col("status") == "COMPLETE")
    .join(customers, orders["customer_id"] == customers["customer_id"])
    .group_by(customers["region"])
    .agg(avg("order_total").alias("avg_order_value"))
    .with_column("computed_ts", current_timestamp()))

result.write.save_as_table("silver.regional_order_kpis",
                           mode="overwrite")

\subsection*{Week 18: Column \& Row Level Security, Data Tagging}
\par\noindent\textbf{Outcomes:} classify PII with object tags, enforce tag-based masking and row access policies, propagate GDPR erasure across schemas, clones, streams, and shares via crypto-shredding, handle legal holds with retention policies.

GDPR right-to-erasure propagation: a deletion request must reach every copy --- raw landing tables, curated Silver/Gold schemas, Snowpipe Streaming channel buffers (within their retention window), Streams (pending CDC offsets replay deletes downstream), zero-copy clones (clones share micro-partitions with the source, so erase in the source then recreate or swap clones), and Reader Accounts / data shares (secure views must filter erased subjects). \section{Appendix A: Glossary}
\begin{description}[leftmargin=4.2cm, style=nextline]
    \item[Micro-partition] Immutable, compressed columnar storage unit (50--500MB) that Snowflake automatically organizes and prunes at query time.
    \item[Virtual Warehouse] Independent MPP compute cluster that executes queries; billed in credits per second while running.
    \item[Cloud Services Layer] Snowflake's coordination plane handling authentication, optimization, metadata, and access control.
    \item[Zero-Copy Clone] Metadata-only copy of a database, schema, or table sharing the same underlying micro-partitions.
    \item[Time Travel] Ability to query, clone, or restore historical table state within the retention window (up to 90 days).
    \item[Fail-safe] Non-configurable 7-day recovery tier after Time Travel expires, restorable only by Snowflake Support.
    \item[Storage Integration] Snowflake object storing IAM/cloud credentials so external stages authenticate without hardcoded keys.
    \item[Snowpipe] Serverless continuous ingestion service loading staged files as they arrive, triggered by cloud event notifications.
    \item[Stream] CDC object recording row-level inserts, updates, and deletes on a source table with a transactional offset.
    \item[Task] Scheduled SQL or stored-procedure execution unit; tasks chain into DAGs via \texttt{AFTER} dependencies.
    \item[Dynamic Table] Declarative table that auto-refreshes from a query within a target lag, building DAGs automatically.
    \item[Snowpark] Developer API (Python/Java/Scala) that translates DataFrame operations into SQL executed inside Snowflake.
    \item[Vectorized UDF] Python UDF processing batches of rows as Pandas DataFrames via PyArrow for near-native performance.
    \item[External Function] User-defined function that invokes a remote REST endpoint through an API Integration and API Gateway.
    \item[RBAC Hierarchy] Role structure separating access roles (privileges on objects) from functional roles (business duties).
    \item[Masking Policy] Column-level policy dynamically obfuscating sensitive values based on the querying role's context.
    \item[Row Access Policy] Policy attached to a table that filters visible rows based on session context such as \texttt{CURRENT\_ROLE()}.
    \item[Secure Data Share] Zero-copy object granting live, read-only access to selected objects across Snowflake accounts.
    \item[Reader Account] Provider-managed account letting non-Snowflake consumers query shared data.
    \item[Data Clean Room] Governed environment for multi-party analytics that computes joins without exposing raw rows.
    \item[Hybrid Table (Unistore)] Row-store table type with primary keys and indexes for OLTP-style point operations alongside OLAP.
    \item[Cortex AI] Snowflake's serverless LLM function family (\texttt{COMPLETE}, \texttt{EMBED\_TEXT}, \texttt{EXTRACT\_ANSWER}) usable from SQL.
    \item[Resource Monitor] Object tracking credit consumption that triggers notify, suspend, or suspend-immediately actions at quotas.
    \item[Snowflake Alert] Scheduled object evaluating a SQL condition and executing an action (e.g. notification) when true.
    \item[Data Metric Function (DMF)] Built-in or custom metric (freshness, volume, null count) scheduled on tables for quality monitoring.
    \item[schemachange] Lightweight Python database-migration tool applying versioned SQL scripts to Snowflake from Git.
\end{description}

    \item Packaged code, data, and UI installed in the consumer's account.
    \item Small cohorts leak individuals; enforce minimum aggregation thresholds.
\end{enumerate}
\noindent\textbf{Week 21:}
\begin{enumerate}[nosep, leftmargin=6mm]
    \item OLTP-style single-row operations alongside analytics.
    \item Enforced primary key, unique, and foreign key constraints.
    \item Row-based storage with secondary indexes suits point access.
    \item One platform serving both transactional and analytical workloads.
    \item For large scans/aggregations where columnar pruning wins.
\end{enumerate}
\noindent\textbf{Week 22:}
\begin{enumerate}[nosep, leftmargin=6mm]
    \item \texttt{COMPLETE} and \texttt{EXTRACT\_ANSWER} (also \texttt{EMBED\_TEXT}, \texttt{SENTIMENT}).
    \item A 768-dimension embedding vector for the input text.
    \item Order by a vector distance function over stored embeddings.
    \item Per token/row; cap with Resource Monitors and pre-filtering.
    \item Text and layout content from documents into queryable form.
\end{enumerate}
\noindent\textbf{Week 23:}
\begin{enumerate}[nosep, leftmargin=6mm]
    \item Versioned, reviewable, reproducible infrastructure across environments.
    \item \texttt{unique}, \texttt{not\_null}, \texttt{accepted\_values}, \texttt{relationships}.
    \item Freshness, volume, or null counts scheduled per table.
    \item Versioned SQL scripts applied in order with a change-history table.
    \item Daily credits vs. trailing 7-day average in \texttt{WAREHOUSE\_METERING\_HISTORY}.
    \item Add nullable new column, dual-write and backfill, switch reads, drop the old column later.
\end{enumerate}
\noindent\textbf{Week 24:}
\begin{enumerate}[nosep, leftmargin=6mm]
    \item Data Movement and Performance Tuning at 30\% each.
    \item Higher depth means more overlapping partitions and worse pruning.
    \item It waits for about six minutes of sustained queuing.
    \item Eliminate options that fight Snowflake's managed-service model.
    \item Re-read the feature docs, then rework the scenario by hand.
\end{enumerate}

\end{itemize}

\section{Appendix F: Portfolio \& Presentation Guide}

\noindent\textbf{GitHub README structure per capstone:} (1) one-paragraph problem statement; (2) architecture diagram first --- reviewers skim; (3) setup steps runnable from a clean trial account; (4) screenshots of pipelines, Snowsight profiles, and alerts firing; (5) cost estimate in credits/storage with optimization decisions; (6) lessons learned, including one failure you debugged.

\noindent\textbf{Resume bullet templates (two per milestone):}
\begin{itemize}[label=-, nosep]
    \item \textbf{M1:} ``Architected a multi-cluster Snowflake backend isolating ETL and BI workloads, cutting query contention by X\%.'' / ``Implemented zero-copy cloning and Time Travel recovery runbooks, reducing environment provisioning from hours to minutes.''
    \item \textbf{M2:} ``Built an event-driven ELT pipeline (S3 $\rightarrow$ Snowpipe $\rightarrow$ Streams $\rightarrow$ Tasks) processing N events/day with idempotent MERGE semantics.'' / ``Designed serverless task DAGs with SNS error alerting, achieving $<$X-minute pipeline latency at \$Y/month.''
    \item \textbf{M3:} ``Re-architected JSON telemetry ingestion into a declarative Dynamic Tables Bronze-Silver-Gold DAG with 5-minute freshness.'' / ``Enforced VARIANT data contracts via CHECK constraints, rejecting X\% malformed records before they reached analysts.''
    \item \textbf{M4:} ``Developed Snowpark Python pipelines with vectorized Pandas UDFs, eliminating data egress to external Spark clusters.'' / ``Shipped a reverse-ETL sync from Snowflake to the CRM via Tasks + External Functions with change-only deltas.''
    \item \textbf{M5:} ``Implemented tag-based dynamic masking and row access policies for GDPR-compliant multi-tenant analytics.'' / ``Published zero-copy Secure Data Shares to N external partners via Reader Accounts.''
    \item \textbf{M6:} ``Automated Snowflake infrastructure with Terraform and dbt CI/CD, deploying schema changes with zero downtime.'' / ``Built cost-anomaly alerting on WAREHOUSE\_METERING\_HISTORY, catching a 2$\times$ credit spike within one hour.''
\end{itemize}

\noindent\textbf{Talking about your project in interviews:} Lead with the business problem and the constraint (latency, cost, compliance), then the architecture in one sentence, then the two hardest trade-offs you made and why. Quantify everything (rows, latency, credits, dollars). When asked what you would do differently, name a real limitation you hit --- e.g., a Dynamic Table falling back to full refresh --- and what it taught you. Interviewers trust candidates who discuss failures concretely.
