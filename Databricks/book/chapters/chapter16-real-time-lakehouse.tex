\section{Week 16 Roadmap and Mental Model}
Part IV's previous chapters built streaming \emph{mechanics}. Week 16 assembles them into \emph{architecture}: a lakehouse where streams and batches write the same governed tables, real-time aggregates serve live dashboards, and a batch path reconciles the streaming view against business truth. This is the chapter where the medallion (Part I) and streaming (Part IV) become one system \cite{sparkStructuredStreaming,databricksDelta}.

The mental model: \textbf{streaming is a latency tier of the lakehouse, not a separate estate}. Bronze streaming tables capture events; Silver applies the same dedup/quality rules as batch, continuously; Gold maintains incremental aggregates. The batch path is not legacy---it is the reconciliation and reprocessing tier that keeps the stream honest.

\begin{definitionbox}
\textbf{A real-time lakehouse} is a medallion architecture whose layers are maintained continuously by streaming pipelines, with batch processing retained for backfill, reconciliation, and heavy reprocessing---one governed storage layer (Delta) serving both latency tiers.
\end{definitionbox}

\begin{keyterms}
\textbf{\texttt{foreachBatch}}: the escape hatch running arbitrary batch logic (MERGE, fan-out) per micro-batch with checkpointed exactly-once. \textbf{Stream-static join}: enriching a stream against a slowly changing table. \textbf{Stream-stream join}: joining two streams with watermarks on both. \textbf{Latency budget}: the end-to-end freshness requirement decomposed per stage. \textbf{Reconciliation}: the batch proof that streaming Gold matches source truth.
\end{keyterms}

\section{Monday: The Streaming Medallion}
\subsection{Layer by Layer}
\textbf{Bronze}: the append stream from Kafka/Auto Loader---exactly-once facts, liquid-clustered for the serving queries. \textbf{Silver}: dedup (watermarked), typing, expectations (DLT streams carry them), and stream-static enrichment against dimensions. \textbf{Gold}: incremental aggregates---windowed revenue, running counts---served directly to dashboards. The batch pipeline still exists: it recomputes Gold nightly from Bronze as the reconciliation of record.

\subsection{One Table, Two Writers}
Delta's optimistic concurrency lets a stream and a batch job write the same table---\emph{if} they write disjoint slices (stream owns recent data; batch owns restatements) or coordinate through keys. The practical pattern: streams write live partitions; nightly batch rewrites the same logical window with reconciled values in a \texttt{replaceWhere} scoped overwrite. Conflicts are commit-time failures you design away by slice discipline, not luck.

\begin{pitfall}
\textbf{Stream and batch both upserting the same keys.} Two writers MERGE-ing the same keyspace will serialize against each other, fail commits under contention, and produce ordering-dependent state. Partition the responsibility: stream owns now, batch owns then; or make the batch the only writer and the stream a staging feed.
\end{pitfall}

\section{Tuesday: foreachBatch and Streaming Joins}
\subsection{foreachBatch: The Correct Escape Hatch}
Streaming DataFrames cannot MERGE directly. \texttt{foreachBatch} hands each micro-batch to a function as a \emph{batch} DataFrame---where MERGE, multiple sinks, and side effects are legal---while the checkpoint still guarantees the batch is processed exactly once:

\begin{lstlisting}[language=Python,caption={foreachBatch MERGE sink: idempotent upserts from a stream.},label={lst:ch16-foreachbatch}]
def upsert_to_silver(batch_df, batch_id):
    batch_df.createOrReplaceTempView(f"batch_{batch_id}")
    spark.sql(f"""
        MERGE INTO de_training.silver.orders_rt AS t
        USING batch_{batch_id} AS s
        ON t.order_id = s.order_id
        WHEN MATCHED AND s.event_ts > t.event_ts THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *
    """)

(stream.writeStream
    .foreachBatch(upsert_to_silver)
    .option("checkpointLocation", "/Volumes/de_training/silver/_ckpt/orders_rt")
    .trigger(processingTime="30 seconds")
    .start())
\end{lstlisting}

\subsection{Streaming Joins}
\textbf{Stream-static} (events $\times$ dimension): the static side is snapshotted per batch---broadcast it when small, and know that dimension changes apply to \emph{new} micro-batches only. \textbf{Stream-stream}: both sides arrive over time; the join needs watermarks on both sides plus an event-time join constraint (\texttt{A.ts BETWEEN B.ts - INTERVAL 5 MINUTES AND B.ts}), which tells the engine when join state can be evicted. Unbounded stream-stream joins without watermarks are unbounded state.

\section{Thursday Hands-on Project: The Real-Time Orders Pipeline}
Build the full streaming medallion for orders: Kafka $\rightarrow$ Bronze $\rightarrow$ Silver deduped MERGE $\rightarrow$ Gold 5-minute revenue $\rightarrow$ a live AI/BI dashboard with a freshness tile.
\index{hands-on lab}\index{real-time lakehouse!lab}

\begin{lstlisting}[language=Python,caption={Week 16 lab: the streaming Gold aggregation.},label={lst:ch16-lab}]
from pyspark.sql import functions as F

silver = spark.readStream.table("de_training.silver.orders_rt")

gold5m = (silver
    .withWatermark("event_ts", "10 minutes")
    .groupBy(F.window("event_ts", "5 minutes"), "region")
    .agg(F.sum("amount").alias("revenue"),
         F.countDistinct("order_id").alias("orders")))

def publish_gold(batch_df, batch_id):
    batch_df.createOrReplaceTempView("g")
    spark.sql("""
        MERGE INTO de_training.gold.revenue_5m AS t
        USING g AS s
        ON t.window_start = s.window.start AND t.region = s.region
        WHEN MATCHED THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *
    """)

(gold5m.writeStream.foreachBatch(publish_gold)
    .outputMode("update")
    .option("checkpointLocation", "/Volumes/de_training/gold/_ckpt/revenue_5m")
    .trigger(processingTime="1 minute")
    .start())

\end{lstlisting}

\subsection{Architecture Decisions}
\textbf{Two tiers, one truth.} The dispatch tier optimizes for freshness: 30-second micro-batches, update-mode aggregates into \texttt{gold.vehicle\_status}, a 1-minute dashboard. The billing tier optimizes for correctness: nightly batch recompute from Bronze with exact dedup and windowing---its Gold is the invoice source. The streaming Gold is explicitly labeled operational; the batch Gold is financial. They agree because they share Bronze, dedup keys, and window definitions---and a daily diff job proves it.

\textbf{Capacity and cost.} Kafka partitioned by \texttt{vehicle\_id} (ordering per vehicle, parallelism for scale); the dispatch stream is the only always-on compute; everything else is triggered. The cost model (\cref{tab:ch16-latency}) is reviewed monthly against the measured freshness dispatch actually uses.

\begin{pitfall}
\textbf{Billing from the streaming tier.} Operational aggregates tolerate late-drop and at-least-once edge cases that invoices may not. The batch reconciliation tier is not optional overhead---it is what makes the real-time tier safe to move fast.
\end{pitfall}

\section{Interview Q\&A}
\subsection{Concepts and Trade-offs}
\begin{enumerate}
    \item \textbf{Q: Why does the stream need a batch shadow at all?}\\
    A: Streams trade exactness for latency: watermarks drop late data, edge cases duplicate, windows close early. The nightly batch from Bronze is the reconciled truth; the stream is the fast approximation that must provably agree with it.
    \item \textbf{Q: Why \texttt{foreachBatch} instead of a native MERGE sink?}\\
    A: Streaming DataFrames do not support MERGE directly; \texttt{foreachBatch} exposes each micro-batch as a batch DataFrame---where MERGE is legal---while the checkpoint preserves exactly-once across the hand-off.
    \item \textbf{Q: Stream-stream join: what makes it safe?}\\
    A: Watermarks on \emph{both} sides plus an event-time interval constraint, so join state is bounded and evictable; without them the join state is unbounded memory.
    \item \textbf{Q: When is continuous processing justified over 30-second micro-batches?}\\
    A: When the measured business cost of 30 seconds of staleness exceeds the DBU premium---rare outside market-making, real-time bidding, and safety systems. Most ``real-time'' requirements are micro-batch requirements.
    \item \textbf{Q: How do you keep the dashboard honest?}\\
    A: A freshness tile showing \texttt{max(event\_ts)} and last-write time, plus an alert when lag exceeds the budget---the dashboard that monitors its own pipeline.
    \item \textbf{Q: Why not query the streaming Silver directly for billing?}\\
    A: Because streams encode lateness and replay policy; billing needs the reconciled batch computation over immutable Bronze. Fast and correct are different tiers by design.
    \item \textbf{Q: What is the cost question to ask before any continuous trigger?}\\
    A: ``What does one minute of staleness cost the business?'' If the answer is unmeasurable, the continuous premium is unpayable-by-logic---choose triggered.
    \item \textbf{Q: What is the migration path from a nightly batch estate to this architecture?}\\
    A: Incremental: Auto Loader replaces file polling, \texttt{availableNow} streams replace cron reads, and only consumers with measured freshness needs graduate to micro-batch triggers. The batch tier remains the reconciler throughout.
\end{enumerate}
